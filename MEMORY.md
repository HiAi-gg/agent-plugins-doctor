# Project Memory — Agent Plugin Doctor

## Architecture Decisions

- **Parser package (Phase 4)**: `@agent-plugins-doctor/parser` is the single canonical implementation for filesystem loading and parsing of plugin components. It replaces Builder's 7 regex-based frontmatter parsers.
- **Vendored schemas**: `packages/parser/src/schemas/{plugin,mcp}.schema.json` are byte-exact copies of the official Agent Plugins v1.0.0 schemas (agent-plugins.org). They are never modified and excluded from prettier via `.prettierignore` (spec requires clients MUST NOT fetch schemas at load time).
- **JSON Schema validation**: AJV v8's 2020-12 export (`ajv/dist/2020`) is used because the vendored schemas declare draft 2020-12 (`$defs`, `const`). Validators are lazily compiled and cached module-level in `src/validation.ts`.
- **MCP per-server failure isolation (§7.2.2)**: `parseMcpConfig` treats top-level violations (bad/missing `$schema`, missing/non-object `mcpServers`, unknown top-level fields, or a server entry whose _value_ is not an object) as fatal `SchemaValidationError`. Invalid server _objects_ are skipped individually; valid servers survive. A missing mcp.json returns `undefined`.
- **Manifest non-fatal fields (§5.2, §8.1)**: unknown top-level `plugin.json` fields and a non-object `extensions` are reported-and-ignored (stripped from the returned manifest) instead of throwing. All other schema violations are fatal `SchemaValidationError`.
- **Rules package (Phase 5)**: 29 rules across 7 categories (manifest→`spec`, skill→`skills`, mcp, security, structure, compatibility, format). Diagnostic codes DOC-1xxx..DOC-7xxx; exit codes 0=clean, 1=errors, 2=critical, 3=internal rule failure (`DOC-0000`); `strict` promotes warnings to failure. `createDefaultRegistry` lives in `src/rules/index.ts` (registry.ts holds only the `RuleRegistry` class to avoid a circular import); rules/index.ts filters module namespaces through `isRule()` before registering (categories also export non-Rule values).
- **Fix engine is text-based + idempotent**: `applyFixes` matches `oldText`/`newText` against the _current_ file content; a fix whose target state is already present is a no-op success. JSON member-removal fixes are computed by a single-pass scanner in `util.ts` (`scanJsonMembers`) producing **targeted spans** that cover the member's leading whitespace through its value **without separator commas** — the engine (`removeJsonMember` in fixes.ts) cleans up the surrounding comma when applying, so removals are order-independent even when several members of the same object are removed in one pass (a sibling removal changing the comma layout no longer breaks a later fix's old text). `fix.newText === ''` falls back to whitespace-tolerant regex matching plus comma cleanup. Directory renames (DOC-2001/DOC-5002) are applied **last** (stable sort) so a content fix on a file inside a renamed directory never fails with ENOENT. Whole-file replace fixes are used only by format rules, which get a re-derive fallback (`canonicalJson` / `normalizeSkillFrontmatter`) when the file changed since check time. DOC-1002 (name-pattern) and DOC-1007 (schema-match) rewrite only the **value token** of their top-level member via `jsonMemberValueSpan` (path-aware, whitespace-tolerant, skipped when the file is missing or the on-disk value no longer matches the in-memory model — a stale SDK model stops offering fixes). Engine registry order (manifest→…→format) plus these mechanisms make `--fix` conflict-free. Audited in `docs/AUTOFIX_AUDIT.md` + locked in by `tests/integration/autofix-idempotence.test.ts`.
- **Raw-file rules**: rules that detect parser-stripped data (`manifest-unknown-fields`, `author-strictness`, `deprecated-fields`) read the raw `plugin.json` from disk, falling back to the in-memory manifest when the file is absent. Fix `fix()` methods identify their target member via a deterministic message-embedded key (internal contract, e.g. `field "foo"`).
- **FixKind in core is NOT extended**: `types.test.ts` pins the union to exactly 4 kinds, so format fixes reuse `kind: 'replace'` with the category-based re-derive fallback instead of adding a `'format'` kind.
- **Compatibility package (Phase 6)**: `@agent-plugins-doctor/compatibility` ships a `ClientProfileRegistry` seeded from `src/data/clients.json` (5 verified clients: vscode, cursor, copilot, codex, kiro — codex is the only one without `mcpLegacySse`). `CompatibilityChecker` is conservative: unsupported spec version / skills / MCP transport → `error` (incompatible); extensions are optional per §8 so never blocking — `extensions: true` (mechanism supported; unknown namespaces safely ignored per §8.2) → no issue, `extensions: false` → `warning`, unverified profile (`evidence: 'none'`) → `info`. Each check carries `extensionsHandling` (`supported|ignored|unsupported|unknown`): `ignored` when the mechanism is supported, `unsupported` when it is not, `unknown` for unverified profiles, `supported` only for explicitly verified namespaces. `extensionsNote` on capabilities clarifies what was verified. All 5 verified clients have `extensions: true`. Compatible = no error-severity issues. Evidence level (`docs|runtime|expected|none`) is copied from each client profile into the check. tsconfig uses `rootDir: "."` (like core/rules) so `tests/**/*` typechecks; `resolveJsonModule` loads the client data statically (cast `as { clients: ClientProfile[] }` because JSON `evidence` widens to `string`).
- **Compatibility levels (FULL/PARTIAL/UNSUPPORTED/UNKNOWN)**: the binary `compatible` boolean was replaced by a `CompatibilityLevel` enum (values `full|partial|unsupported|unknown`) defined in `packages/compatibility/src/types.ts`; `CompatibilityCheck` also carries `working`/`unsupported` capability-id arrays (`CapabilityId`: `skills|mcp-stdio|mcp-streamable-http|mcp-sse` — `extensions` was REMOVED from the set, extensions never appear in these lists). Level derivation in `checker.ts` `determineLevel`: unsupported spec version → UNSUPPORTED; client profile `evidence: 'none'` → UNKNOWN; no unsupported capabilities → FULL; every used capability unsupported → UNSUPPORTED; otherwise PARTIAL. Extensions are OPTIONAL (info/warning only) and excluded from `working`/`unsupported`, so they never downgrade a check from FULL. `compatible` is derived (`level === FULL`) and kept for backward compat; `ValidationResult.compatible` (top level) remains diagnostics-based (validation validity), unchanged. Core keeps its own `CompatibilityLevel` string-union type (identical values) in `diagnostics.ts` — core is dependency-free so it CANNOT import the enum from compatibility (would create a workspace cycle); the CLI bridge `toCoreCompatibility` in `cli/src/utils/run.ts` converts (string enums are assignable to their literal unions in TS 5.x, no cast needed). Report formatters render levels: human `✓`/`~`(yellow)/`✗`(red)/`?`(dim) with `(level)` suffix for non-full, markdown `✓ Compatible`/`~ Partial`/`✗ Unsupported`/`? Unknown`; the `compatibility` CLI command exit code still uses `check.compatible` (non-FULL → exit 1).
- **v1.0.0 deprecates nothing**: `deprecated-fields` (DOC-6002) is a factory `deprecatedFieldsRule(map = DEFAULT_DEPRECATED_FIELDS)` with an empty default map — silent on v1, mechanism tested with custom maps.
- **Security rules are conservative**: secret detection only fires on strong value patterns (≥16 chars, PEM/AWS/GitHub/sk- prefixes, credential-bearing DB URLs) and skips placeholder-shaped values (`<...>`, `your-`, `xxx`, `changeme`, `...`); messages redact values. Symlink-escape skips missing roots (no false positives).
- **Loader failure isolation (§11.3)**: `loadPlugin` propagates plugin.json errors (fatal), but isolates mcp.json, skill, and extension failures to their component type. Invalid skills/mcp are skipped; the rest of the plugin loads.
- **Code style**: single quotes. `.prettierrc` (`singleQuote: true`) added because the repo had no prettier config; default prettier (double quotes) would conflict with the existing style.
- **Report package (Phase 7)**: `@agent-plugins-doctor/report` renders ValidationResult as human/JSON/Markdown. `getFormatter(format, options)` dispatches; `HumanReportFormatter` is the only one taking `ReportOptions` (`noColor` disables chalk, `verbose` adds `Rule: <id> (<category>)` lines). Color level is resolved at construction from `noColor` → `FORCE_COLOR` → `NO_COLOR` → ambient `chalk` (`new Chalk({level})`, chalk 5 exports `Chalk` as a value + `ChalkInstance`/`ColorSupportLevel` types), so tests are TTY-independent. Human output groups diagnostics by file (worst-severity order, then alpha); markdown groups by severity (Critical→Error→Warning→Info), with severity groups > 5 wrapped in `<details>`; JSON keeps input order and null-pads `file`/`range`/`fix` for stable field ordering (`counts` fixed order error/warning/info/critical; `byCategory` omits zero categories). Shared helpers in `src/util.ts`: `normalizeFilePath` (strips leading `./`), `sortDiagnostics`, `worstSeverityRank`, `wrapText` (80 cols), `titleFromRuleId` (drops leading category word, uppercases known acronyms like `json`→`JSON`). Report tsconfig uses `rootDir: "."` so `tests/**/*` typechecks (same as core/rules). Summary section uses fixed plural labels (`Warnings:` even for count 1); result line pluralizes normally (`1 warning`).
- **CLI package (Phase 8)**: `@agent-plugins-doctor/cli` is a thin commander wrapper with 4 subcommands (`check`, `fix`, `report`, `compatibility`). `src/utils/run.ts` `loadAndValidate()` loads + validates + merges compatibility, mapping compatibility-package `CompatibilityCheck[]` (issues are objects) onto core `CompatibilityResult[]` (issues are `string[]`) — the report formatters need the core shape. Exit codes: `computeExitCode` (priority DOC-0000→3 > critical→2 > error→1 > strict-warning→1 > 0); load/parse/SchemaValidation errors → 3 via `handleCommandError`. `fix` re-loads the plugin from disk after `applyFixes` so raw-file AND in-memory rules see the changes, then re-validates; `--dry-run`/`--yes` gate application, readline prompt otherwise. Commander `--no-color` sets `options.color === false` (there is no `options.noColor`); `parseAsync` (not `parse`) is used so `process.exitCode` is set after async actions complete. Tests drive a fresh `createProgram()` per run with `exitOverride()` (CommanderError carries `.exitCode`) and capture `process.stdout.write`/`process.stderr.write` (console.log would bypass the override in bun). `bin/agent-plugins-doctor` (shebang `#!/usr/bin/env bun`) imports `main()` from src; package.json `bin` points at it.
- **CLI tests use disk-loadable fixtures only**: several rules are unreachable from disk because the vendored schemas already enforce them — `mcp-reserved-env-keys` (PLUGIN_ROOT/PLUGIN_DATA are `propertyNames.not.enum` in mcp.schema.json), `manifest-name-pattern`/`name-length` (schema `pattern`/`maxLength`), `schema-match` (`$schema` is `const`), `mcp-cwd-pattern` (`cwd` has the same schema pattern). Disk-reachable error-with-fix fixtures: duplicate headers in a streamable-http server (DOC-3006 header-validation, `findDuplicateJsonMemberSpans` dedupes; duplicate JSON keys are schema-valid since parse keeps the last), unknown manifest field (DOC-1004 warning + member-removal fix — parser strips the field non-fatally), skill dir/frontmatter name mismatch (DOC-2001 + rename fix). Security fixture: stdio env value `sk-...` (≥16 chars, matches sk-prefix pattern, not a placeholder) → DOC-4003 critical.

- **Skill load failures surface as DOC-2099 parse diagnostics (Phase 1.1b)**: `loadPlugin` now returns `LoadResult` `{ plugin, parseDiagnostics }`. ## Discovered Knowledge / Gotchas

- **js-yaml v3 re-parse quirk** (via gray-matter): re-parsing the _exact same_ malformed YAML string after a first throw silently returns `{}` instead of throwing again. The first parse always throws. Tests that check malformed-YAML errors must parse the content exactly once (capture error in try/catch) rather than calling the parser twice.
- **YAML plain scalars cannot contain `: ` (colon + space)** — js-yaml throws. Colon-in-value tests must use quoted values or colons not followed by spaces.
- **YAML block scalars (`|`) preserve a trailing newline**; `parseSkillFrontmatter` applies `trimEnd()` to description/license/compatibility.
- **gray-matter** ships its own `gray-matter.d.ts` typings (no `@types/gray-matter` needed — that package 404s on npm).
- **AJV standalone `$defs` compile fails**: compiling `#/$defs/server` standalone throws "can't resolve reference" for sibling `$ref`s. Register the full schema via `ajv.addSchema(mcpSchema)` first, then compile `{ $ref: '<schemaId>#/$defs/server' }`.
- **`skills/*/SKILL.md` inside a JSDoc comment breaks parsing** — the `*/` sequence prematurely closes the block comment.
- **tsconfig rootDir**: parser uses `rootDir: "."` (like core) so `tests/**/*` is inside rootDir; `rootDir: "./src"` with tests included causes TS6059. The ROOT `tsconfig.json` (which includes `packages/*/tests/**` and `tests/**`) also needs `rootDir: "."` — the inherited `./src` made `tsc -p tsconfig.json` fail with TS6059 for every package test file.
- **Root tests import workspace packages via root devDependencies**: bun resolves `@agent-plugins-doctor/*` from `tests/` only because the root `package.json` declares them as `workspace:*` devDependencies (bun symlinks them into `node_modules`). Without that, `Cannot find module '@agent-plugins-doctor/core'` from root-level test files.
- **No rule currently emits `range`**: all 29 rules attach `file` but never `range`, so "line numbers" in diagnostics are only available where a range is set (none today). Integration tests assert `file` correctness and validate `range` shape defensively when present.
- **Prettier vs Doctor canonical JSON conflict**: prettier collapses short JSON arrays onto one line; Doctor's `canonicalJson` (JSON.stringify 2-space) expands them. Any self-hosted `plugin.json` must be prettier-ignored or `check .` reports DOC-7001.
- **resolvePluginPath is transitive**: resolving a file against an already-realpath'd directory (e.g., extension.json against the resolved extension dir) preserves containment against the plugin root.
- **tmpdir() may be a symlink on macOS** (`/var/folders/...` → `/private/var/folders/...`): `resolvePluginPath` returns the REAL path (`realpathSync`), so tests that compare with `isWithinPath(result, root)` against the lexical `mkdtempSync` root FAIL on macOS. Tests must compare against `realpathSync(root)` (e.g. `const realRoot = realpathSync(root)`), as in the three `resolvePluginPath` tests in `packages/core/tests/path.test.ts`.
- **Fixture files must be tracked by git**: rules like `structure-extra-files` read the fixture directory LIVE at runtime (`readdirSync`), so any file a test's DOC contract depends on (e.g. `complex-plugin/notes.log` → DOC-5003) MUST be committed. `notes.log` was silently excluded by `.gitignore` `*.log`, so fresh checkouts/CI lost it and `rule exclude filter drops rules` failed inconsistently. Fix: targeted negation `!tests/fixtures/complex-plugin/notes.log` in `.gitignore` + commit the file. When adding a fixture file, verify `git check-ignore` does NOT match it.
- **`isWithinPath` must use the platform separator, never a hardcoded `/`**: `node:path.normalize`/`resolve` return backslash-separated paths on Windows (`C:\plugin\skill.md`), so `startsWith(parent + '/')` rejected EVERY contained path → `resolvePluginPath` threw "Path escapes plugin root" for all valid plugins → 128 tests failed on windows-latest CI (benchmarks, e2e, integration, core, parser, rules) with cascading JSON-parse/exit-code errors. Fix: append `path.sep` and tolerate parents already ending with a separator (drive roots `C:\`). POSIX behavior is unchanged. Linux/macOS CI passing is NOT proof of Windows passing — always watch the windows-latest leg. Related Windows traps: `normalize('/a//b/../c')` → `\a\c` (tests must compare against the platform result), and `resolvePluginPath` returns backslash paths so tests must assert with `endsWith(join(...))`, not `endsWith('/...')`.
- **Real Builder output (v0.0.6, commit 7a0b9bd8) validates cleanly (Phase 1.1c — cross-repo)**: cloned + built https://github.com/HiAi-gg/agent-plugin-builder and generated plugins with each command (`init --name test --description test --yes`, `create --skills-only`, `create --mcp-only --mcp-type stdio --mcp-command node --mcp-args server.js`, `migrate --from claude`, `migrate --from cursor`). Enforced by `tests/integration/builder-real.test.ts` (4 tests) + e2e `check` matrix (23 fixtures now). Builder's `init` has NO `--stdin` flag (the old plan's `echo {...} | init --yes --stdin` is invalid; use `--name/--description/--yes`). Results in `docs/BUILDER_REAL_INTEGRATION.md`.

## Patterns

- Error hierarchy in `src/errors.ts`: `ParseError` (unreadable/invalid JSON/YAML), `SchemaValidationError` (with `errors: SchemaValidationErrorDetail[]` mapped from AJV ErrorObjects), `LoadError` (loader-level: missing root/plugin.json/escapes).
- AJV error mapping: instancePath → `path` (root → `/`), enriched messages for `required`/`additionalProperties`, keyword preserved.
- All plugin-relative path access goes through `resolvePluginPath` (security boundary): manifest escape → reject plugin; SKILL.md escape → skip skill; mcp.json escape → MCP disabled; extension escape → extension skipped.
